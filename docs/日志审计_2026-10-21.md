## 1. 高

### H1 区域求援交互 `is_shown` 刷错，撑爆日志上限，并造成卡顿【已证实】
- **证据**：`common/character_interactions/WJ_district_aid_interactions.txt:15`，`primary_title trigger [ Failed context switch ]`。**49,982 条，全部在 07:49:58–07:50:08 这 10 秒内**，占 error.log 总额度的一半。
- **原因**：`ai_targets = { ai_recipients = realm_characters }` 加上 `ai_frequency = 3`，AI 每季度会把整个国内的所有角色（大部分是无地廷臣）逐个代入 `is_shown`。第一行就是 `scope:recipient = { primary_title = {...} }`，无地角色没有 primary_title，所以每个人都报一次错。日志截断前只看到这一次 10 秒的爆发；按 `ai_frequency` 推断，区域核心（`wj_dd_core`）出现以后每个季度都会重复一次。
- **影响**：
  1. 日志被截断，之后的报错全部丢失。
  2. 每季度一次的大量触发器求值加上写日志，造成卡顿尖峰。
- **方案**：
  1. `is_shown` 第一行改成 `scope:recipient = { is_landed = yes primary_title ?= { tier = tier_kingdom has_variable = wj_dd_core } }`。先做最便宜的过滤，并且用 `?=` 防止报错。
  2. 可以进一步把 `ai_targets` 收窄（例如只取 liege / 同一 top_liege 下的王国级封臣），减少候选人数。

### H2 剧本「撤销文件」用 `holder = 0` 清空郡县无效，造成跨剧本泄漏【原因已证实，后续剧本的影响属推断】
- **证据**：
  - `titlehistory.cpp:355`「Land associated barony/county … is given a null holder」，22.11.14 和 89.1.31 各 1,907 条，共 3,814 条，来自 `history/titles/zz_hd_22_undo.txt` 和 `zz_hd_89_undo.txt`。
  - 184.1.1 出现 214 个郡「holder … is not alive. Hole in history discovered」，见附表 `184开局历史空洞郡.csv`。
  - 已逐一核对：这 214 个郡全部出现在 89 头衔文件和 89 撤销文件里。引擎不允许用历史把郡/县设为无主，所以 `holder = 0` 被忽略，89 剧本的首领一直持有到 184 年。到 184 年这些人都已经死了，于是形成历史空洞。
- **184 开局的实际后果**：存档核对显示，这 214 个郡到 195 年全部有主。但它们在 184 历史里本来没有指定持有人，所以现在的持有人不是设计安排的。持有人具体是谁、怎么来的（推断是引擎填补空洞时找的继承人或生成角色），这次没能从存档里确认。另外，**其中 83 个郡在 `history/characters/zz_hd_fallback_county_holders_184.txt` 里已经有专属的兜底持有人（`hd_fallback_holder_c_*`），但没有任何头衔文件把郡分给他们**。
- **对后续剧本的风险（推断，未实测）**：`zz_hd_263_undo.txt`（1,823 处）和 `zz_hd_304_undo.txt`（2,344 处）也是同样写法。本次是 184 开局，日期在后面的撤销条目不会执行，所以没有报错。但从 304/346/370/404/531 开局时，前一个剧本的郡持有人会漏进来；剧本之间相隔 24–42 年，**持有人如果还活着，就会真的占着这个郡**。
- **方案**：
  1. 撤销生成器（gen22/gen89/gen263/gen304 等）不要对 `c_`/`b_` 头衔写 `holder = 0`。改为在每个后续开局的头衔文件里，给所有「被前面剧本写过」的郡显式写上该开局的持有人。
  2. 184 开局先把这 83 个郡写成 `184.1.1 = { holder = hd_fallback_holder_<郡> }`，其余 131 个郡指定持有人或新建兜底人物。
  3. 修完后分别从 304/346/370/404/531 开局，检查 error.log 里没有「null holder」和「Hole in history」。

### M4 开局人口清除的「随机」仍然不随机：10-11 的修复无效【现象已证实；原因属推断】
- `common/scripted_effects/zz_hd_popclean_effects.txt:11` 报「range directive used, but no randomization is available」，共 4,822 条。也就是每个候选人都报一次。
- **原因（推断）**：随机数写在具名脚本值 `common/script_values/zz_hd_popclean_values.txt:37`（`integer_range`）里，在 `set_variable` 中通过具名值引用时可能拿不到随机上下文。原版 `grab_gold_fuzz_number_effect` 的注释也提到要把随机放在效果里做。10-11 改成「隐藏事件触发」没有解决这个问题。
- **影响**：同一档位内的排序没有随机性，每局清掉的都是同一批人。本局候选只有 4,822 人，少于目标 7,000，所以这次实际上全部被清除。
- **方案**：
  1. 照原版做法，把随机直接内联写在效果里：`set_variable = { name = hd_popclean_key value = { value = hd_popclean_tier_value multiply = 1000 add = { integer_range = { min = 0 max = 999 } } } }`。
  2. 如果内联后仍然报错，说明原因是「与开局同一帧执行」。那就把 `hd_popclean.2` 改为 `trigger_event = { id = hd_popclean.2 days = 1 }` 延迟一天再触发。

### M6 1.6 万条「'10000'..'26249' is not a valid event ID」：原因已查明，运行时影响未证实【原因已证实；影响属推断】
- 10-11 以来一直没查明的五位数事件 ID，现在找到了来源：**每个带 `effect` 的 on_action 引擎都会占用一个内部编号，上限是 1 万**。原版加 mod 共有 26,799 个 on_action（与 debug.log 里「Total of : 26799」一致），其中带 effect 的有 26,249 个，与报错上界 26249 吻合。多出来的主要是 `common/on_action/zz_hd_hbirth_generated_on_actions.txt` 的 25,405 个「每人一个」on_action。10-11 时报错是 2,182 条，OE 人物整合之后涨到了 16,250 条。
- **本局没有观察到功能损失**：按文件顺序排在 1 万以后的 `hds_heartbeat`（执行 60 次）、`hd_184_office_cap_step`（34 次）、`hd_historical_revolt_monthly_check`（122 次）都正常执行了。hd_hb 只执行了 2 个，这是排期本来如此：184、185 年各 1 人，186–194 年没有人。
- **风险（未实测）**：
  1. 这 1.6 万条报错占掉了 16% 的日志额度。
  2. 编号超限的延迟 on_action 在存档、读档之后是否还会触发，没有验证过。
  3. 每年的出场批次挂在**同一个随机 AI 独立君主**身上（`hd_hb_pick_carrier_effect`）。这个人如果在一年之内死亡，当年还没触发的出场可能整批丢失。
- **方案**：生成器改掉「每人一个 on_action」的结构。改成按年月分桶的 scripted_effect，例如生成器为每个人预先随机分配出场月份，生成 `hd_hb_m<年月>_effect`，由 monthly pulse 直接调用。这样不再需要 on_action，也不依赖载体角色。临时验证办法：存档后读档，确认已经排期的人物照常出场。
